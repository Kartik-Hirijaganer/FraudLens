## Full live measurements

### Raw model levels

| Concurrency | AWQ p95 | BF16 p95 | AWQ req/s | BF16 req/s | AWQ gate pass | BF16 gate pass |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 3.214 s | 6.365 s | 0.354 | 0.185 | 898/1,000 | 994/1,000 |
| 8 | 6.741 s | 8.379 s | 1.650 | 1.134 | 906/1,000 | 993/1,000 |
| 32 | 16.228 s | 16.164 s | 2.459 | 2.399 | 909/1,000 | 995/1,000 |

At c32, full-run AWQ raw p95 was 0.4% higher and request throughput 2.5% higher than BF16. The
40-case development improvements did not reproduce at the full population. These full-run raw
levels used the same RTX 4090 SKU, image, corpus, prompt, and protocol but different physical
hosts, whose drivers were `580.159.04` and `580.178.04`. Treat their small c32 deltas as diagnostic,
not as a new equal-host quantization headline. The immutable v1 report remains the support for the
older equal-hardware raw AWQ comparison.

The three terminal failures had no citation evidence and were rejected before any provider call.
Their case ids are `ibm-hi-small-008905-469ef18b`, `ibm-li-medium-002577-078353c9`, and
`ibm-hi-small-004104-c42acafe`. The run retained their stable policy error but the harness version
used for generation did not persist the detailed gate reason on a zero-attempt row. The post-run
composer fix treats these as zero-model-call cases and retains reasons in future runs; it does not
alter the captured evidence or rerun a failed case.

The quality summary evaluates the 997 analyst-visible accepted drafts, not the 92 discarded AWQ
attempts. All accepted drafts were schema-valid and used only offered citation ids. The separate
benchmark usefulness check passed 926/997 because it adds expected-citation-recall and fact-
coverage targets that are intentionally stricter than the runtime production gate.

## Memory result

AWQ parsed model weights were 5.2036 GiB versus 14.2488 GiB for BF16, a 63.5% reduction. This is
weight memory, not total device occupancy. vLLM reserves remaining memory for KV cache, and the
two-endpoint cascade peaked at 43,540 MiB in aggregate. Phase 5 must keep those quantities separate.

## What the result supports

Supportable engineering statement:

> Designed and live-benchmarked a production quality-gated AWQ→BF16 SAR cascade over 1,000
> synthetic cases; 9.2% escalated, final gate pass reached 99.7% versus 99.5% for BF16 alone, and
> the quality gain carried a 6.3% c32 p95 latency overhead.

The 63.5% model-weight reduction may be stated separately. Do not say the cascade reduced p95,
do not attach the old 36.3%/60.8% raw-model figures to the cascade, and do not call the v5 route
constrained decoding: generation is unconstrained, deterministic hydration closes trusted fields,
and the unchanged production gate controls acceptance and escalation.

These are deliberately human-owned and are **not** done:

1. **Rotate `VLLM_API_KEY` in Infisical `prod` `/ml`.** The key was written to an unencrypted

2. **Migrate the RunPod operator to REST v2 — decided for the NEXT paid session, not this one.**
   The owner reviewed the inventory on 2026-09-18 and chose to stay on `rest.runpod.io/v1` for
   release 0.5.0: all three mid-release `/v1` breakages are patched, and 0.5.0 provisions nothing
   further. The migration is an **admission precondition for the next paid GPU session**, and it
   lands behind a short owner-approved single-pod smoke (ledger row, teardown, verify-clean)
   because no v2 rewrite can be validated against the provider without one — a green
   fake-transport suite is not the provider accepting the body.

   The inventory is recorded here so the next session does not re-derive it.

   *Mechanical, low-risk:*

   | v1 | v2 |
   |---|---|
   | `https://rest.runpod.io/v1` | `https://api.runpod.io/v2` |
   | `GET /pods` → bare array | `GET /v2/pods` → `{"pods": [...]}` |
   | `GET /networkvolumes` | `GET /v2/network-volumes` (hyphenated; `/v2/networkvolumes` is a 404) |
   | `POST /pods/{id}/start`, `/stop` | `POST /v2/pods/{id}/action` with `{"action": "start"｜"stop"}` |
   | `imageName`, `containerDiskInGb` | `image`, `disk` |
   | `volumeInGb` + `volumeMountPath` | `mounts.persistent.{size, path}` |
   | `gpuTypeIds` + `gpuCount` | `gpu.{id, count}` (single type, not a fallback list) |
   | `allowedCudaVersions` | `gpu.allowedCudaVersions` |
   | `cloudType` | `cloud` |
   | `desiredStatus` | `status` (gains `PROVISIONING`, `STARTING`, `ERROR`) |
   | `publicIp`, `portMappings` | `runtime.ports[]`, populated only while `RUNNING` |

   *The real fork — capabilities v2 removes that this operator depends on:*

   | Lost | Where it is used today | Why it matters |
   |---|---|---|
   | `minRAMPerGPU`, `minVCPUPerGPU`, `minDownloadMbps` | `CreatePodRequest` (`models.py:73-81`) | Host-quality floors that refuse an underpowered host **before** renting it. AD-4.2's equal-hardware comparison rests on them. |
   | `interruptible`, `locked` | `validate_pod_contract` (`session.py:90`) | v2 has no spot pods on this path, so the guarantee becomes structural rather than asserted — but the assertion disappears. |
   | `volumeEncrypted` | `validate_pod_contract` (`session.py:98`) | Already a judged exception (ADR-030); v2 formalises it by having no such field at all. |
   | `machine.secureCloud` | `validate_pod_contract` (`session.py:104`) | `machine{}` is gone; only `dataCenterId` survives. The **request** still asserts `cloud: "SECURE"`, so only the result-side check is lost. |

   Also note `mounts.persistent` is itself deprecated in v2 and is host-local — data does not
   survive a host failure. That is acceptable for this workload (model weights re-download and the
   API key is re-injected), but it should be a stated choice rather than a literal translation of
   `volumeInGb`.

   The recommended shape when it is done: migrate, and replace the lost create-time floors with
   **post-create verification** against `GET /v2/catalog/gpus` and the pod's `runtime` block,
   failing closed and terminating an under-spec pod. That keeps the guarantee and only moves where
   it is enforced.

## Operational defects retained for the record

The earlier live attempts found and fixed: rejected `volumeEncrypted` create fields, an empty
`publicIp` orphan hazard, unavailable encryption reporting, MooseFS stale handles and ignored
permissions, vLLM's positional model argument, missing case-manifest sync, profile-derived case
path drift, archive checkouts without Git metadata, gate-rejected warm-up misclassification,
single-endpoint environment mapping, remote telemetry identity, and cache leakage between
concurrency levels. Their adverse artifacts and full chronology remain in the plan and ledger.

The most valuable future prevention is a five-minute throwaway 125M-model smoke Pod exercising
create → sync → serve → complete → export → teardown, plus a read-only live RunPod response-contract
check before creation. RunPod REST v2 migration remains Phase 5 hardening.
