## How the final session cleared the defects

These changes were applied and covered before the corrected final session:

1. Commit provenance is injected from the commit-bound RunPod session into archive checkouts.
2. The process runtime emits positional `vllm serve <model>` arguments.
3. Sync transfers the corpus and its manifest sidecar together.
4. The vLLM API token and Python environment live on container disk, not the unencrypted MooseFS
   volume; dependency sync uses copy mode.
5. Gate rejection is a measured verdict, not a serving failure, and named endpoint variables are
   populated for the production drafter.
6. Startup logs, telemetry, and immutable GPU identity are queried independently for each role.

The remaining provider-maintenance item is REST v2 migration. It is Phase 5 hardening, not an
explanation for the final adverse result: the final run reached both models and the production gate.

### The one addition that would have caught all nine

A **throwaway smoke Pod** (~$0.07, five minutes) with a 125M-parameter model, exercising
create → sync → serve → one completion → teardown, run before any full session. Add it as a
`make` target and put it in the `benchmark-vllm` skill ahead of the existing smoke step, which
currently sits *after* provisioning and therefore assumes the part that broke.

A second cheap guard: a **read-only contract check at plan time** that GETs the live pods endpoint
and validates the response against `RunpodPod`. Free, and it catches provider drift before a Pod
exists.

## Hard constraints — do not work around these

- **Golden Rule 1.** No commit or push without explicit human permission. The owner granted
  per-run operational commits for the 2026-09-17 session only; that grant does not carry forward.
- **Golden Rule 7.** No billable or mutating cloud action without explicit permission. That
  includes `runpod-gpu-{up,down,start,stop,sync}`, all of which are ask-gated in
  `.claude/settings.json`.
- **A Pod is bound to the commit its session records.** `sync_session` refuses when local `HEAD`
  differs. This is deliberate: it stops two endpoints running different source, which would void
  the comparison. **Consequence: never commit between creating a Pod and syncing it.** Doing so
  costs a full teardown and rebuild — it happened once in this session.
- **Provenance must never be fabricated.** If a value cannot be obtained honestly, fail and record
  the absence, as the volume-encryption exception does.
- **The v1 report is immutable evidence** (AD-1.3). `config/vllm-bench.yaml`'s `protocol_lineage`
  keeps it hash-bound under protocol v2; do not remove that entry.

### Two-endpoint topology — decide and record this

The plan says both endpoints must be "simultaneously reachable" but never says *from where*, and
the answer changes the measured escalation latency. Each vLLM binds loopback and only `22/tcp` is
exposed. In this session the client ran **on the AWQ Pod**, reaching BF16 through an SSH tunnel
over RunPod's network, using an ephemeral key generated on container disk. Running the client
locally instead would add operator-network latency to every escalated case — the exact figure the
release reports. Whatever is chosen, state it in the report's methodology.

## What the evidence currently supports

The live development pilot supports a narrowly worded raw-model claim: on the same RTX 4090 at c32
over 40 synthetic development cases per arm, AWQ reduced parsed weight memory by 63.5%, increased
request throughput by 47.2%, and reduced p95 by 25.7%. It is not a full-profile result.

The live production-cascade evidence supports only an adverse claim: prompt-v2 constrained
generation reached both models with zero serving errors, but 100% of the eight smoke cases
escalated and none passed the final gate. The committed 1,000-case replay remains a reproducible
projection, but it must now be presented next to this divergent live result—not as a substitute for
it. The evidence does not support `reference_validity == 1.0` for BF16, cascade final pass ≥0.99,
or the original gated-cascade resume bullet. Those claims require a versioned remediation and a
new admitted live run.
